# Work with portfolio-2022

Read the checkout's `AGENTS.md`, package scripts and current source before making claims or changes. This is reusable, repo-scoped engineering knowledge—not a frozen implementation, Bembel configuration, orchestration guide or generated trace. Reuse current helpers/components and state owners rather than assuming a pilot feature or pending-state helper exists. The assignment controls write authority: remain read-only when reviewing, and do not start the development server or create commits without explicit current user authorization.

Use Node 24 and npm 11 or newer; select the repository runtime with `nvm use` before installation and checks (source `${NVM_DIR:-$HOME/.nvm}/nvm.sh` first if nvm is not initialized). Use `npm ci` when locked dependencies need installation; missing `vitest`, `tsc` or ESLint dependencies mean setup is incomplete, not that a check passed. Run relevant existing package scripts: `npm test`, `npm run typecheck`, `npm run lint`, `npm run format:check` and `npm run build`. Use the project-local formatter on touched files and avoid broad unrelated rewrites. Report setup failures and each executed check truthfully; do not imply unrun checks passed.

The application uses Vite, React, React Three Fiber/Drei, Three.js, Rapier, Tailwind and Zustand. Entrypoints are `src/main.tsx` and `src/App.tsx`. Inspect `src/store/store.ts` for presentation, selection and active gather state; `src/features/rapier/RapierItems.tsx` for body readiness, frame updates, steering and interaction; and `src/features/physics/` for scene constants and item descriptors. Data lives under `src/data/`, with assets under `public/` and `src/assets/`.

Presentation state and visible 3D movement are distinct. Assets and rigid bodies initialize asynchronously. For entry paths such as URL-driven selection, trace both state transition and actual scene readiness. Do not let a timed gather expire before required bodies exist: pending gather work should remain pending until all required assets/bodies are ready, then receive a usable gather interval rather than an already-expired timer. Replacement, close and cancellation must clear or supersede pending work so it cannot activate later. Inspect implementation before choosing lifecycle handling; do not assume a particular helper exists. When changing this lifecycle, add a regression that explicitly delays required readiness beyond the ordinary gather window, verifies the pending action survives and starts with usable time once ready, and verifies replacement or close/cancellation prevents stale activation.

Store/component tests can establish their own contracts but cannot prove Rapier movement or rendered-scene behavior. For scene interactions, direct-entry/reload, Back/Forward, clipboard outcomes or responsive overlays, use authorized browser verification against the intended running app and report observations. Check browser verification in separate observable steps: an open Chrome window establishes only the browser process; a successful DevTools connection establishes the debugging endpoint; a response from the intended application at its assigned URL establishes app serving. None alone proves the scene feature works. Do not combine an open window and a working debugging connection into one assumed prerequisite. Use a supplied URL/port when available; otherwise derive startup from the repository's Vite command. Do not switch project, profile or port silently after a collision.

Keep changes focused and preserve item presentation, group selection, sorting, scene interaction and responsive behavior unless intentionally changed. Add small meaningful regression coverage using existing Vitest/Testing Library conventions. Capture concrete reproducible friction as a local incident only when supported; capture does not authorize skill changes, inference or publication.
